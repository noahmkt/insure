# PRD — 내보험 찾기 (실손보험 청구 간소화 앱)

버전 v1.0 / 2026-07 / 원문 사양서 기반 세부화. **[법적 하드 룰]**(§3)은 어떤 경우에도 변경·완화 불가.

## 1. 제품 정의

**"내가 놓친 보험금을 찾아주고, 청구까지 가장 쉬운 길로 안내하는 B2C 앱"**

- 청구 '실행 도구'가 아니라 청구 **발굴·안내·관리 레이어**.
- 실행(최종 제출)은 공식 채널(실손24·보험사)에서 **고객 본인**이 수행.
- 수익은 청구가 아니라 **보험 분석 → 전문가 상담 연결(리드)** 에서 발생.

### 1.1 포지셔닝 원칙

- 실손24와 동일 기능 경쟁 금지. 실손24가 하지 않는 영역에만 집중:
  미청구 진료 자동 발굴 / 예상 환급금 계산 / 내 보험 통합 관리 / 미연계 병원 청구 가이드 / 가족 청구 관리 / 전문가 상담 연결.
- 핵심 훅: 연간 약 3천억 원 미청구 소멸 → 첫 화면 **"예상 환급금 ○○원"** (토스 '숨은 돈 찾기' 공식).
- 성공보수형 청구대행 모델(무자격 손해사정·변호사법 그레이존)은 **채택 금지**. "발굴·정리·안내 + 상담 연결" 구조가 차별화 포인트.

## 2. 핵심 개념 구분 (전 화면·전 문구·전 스키마 공통)

| 구분 | 정의 | 데이터 성격 | 표기 원칙 |
|---|---|---|---|
| 숨은보험금 | 만기·중도·휴면 등 지급 확정·미수령 금액 | **확정액** (내보험찾아줌 조회 결과) | 금액 그대로 표기 |
| 미청구 보험금(실비) | 진료내역 × 보험 담보 매칭 예측 금액 | **예측액** | "예상" 접두 + 산출 근거 노출 + 면책 문구 |

- DB: `confirmed_benefits` 테이블과 `matching_results`(예측) 테이블로 물리적 분리.
- API: 응답 스키마 분리(`ConfirmedBenefitDto` vs `EstimatedRefundDto`), 예측 DTO는 `disclaimer` 필드 강제.
- UI: 합산 노출 시에도 구분 뱃지(확정/예상) 필수.

## 3. [법적 하드 룰] — 위반 불가

1. **손해사정·청구대행 금지**: 대행·성공보수 금지. 서류 준비·검토·안내까지만. 최종 제출은 고객 본인(실손24 딥링크 또는 보험사 채널). 손해사정 성격 "검토"는 정식 자격 손해사정사 채용/제휴 범위 내에서만.
2. **주민등록번호 원문 저장 금지**: CI 기반 식별(PASS·카카오). 스크래핑 API가 주민번호를 요구하면 pass-through(조회 시점 메모리 사용 → 즉시 폐기, 로그·백업 포함 완전 미저장). 개인정보보호법 제24조의2.
3. **민감정보(진료내역) 별도 동의**: 개인정보보호법 제23조. 분리 동의 + 암호화 저장 + 역할 기반 접근통제.
4. **동의 4층 분리**: 수집·이용 / 민감정보 / 제3자 제공 / 마케팅. 포괄 동의 금지. 제3자 제공은 **상담 신청 버튼 클릭 시점** 명시 동의.
5. **목적 외 이용 금지**: 청구 지원용 진료내역 동의를 보험 영업에 사용 금지. 청구 지원용/보험 분석·상담용 동의는 별개.
6. **모집행위 규제**: 설계사 연결은 보험업법 모집/모집광고 규제 검토 완료 후 오픈. GA 설립 또는 제휴 전제. 문구는 "전문가 상담 신청" 프레임.
7. **면책 문구 고정**: 모든 예측 금액 화면에 "실제 지급액은 보험사 심사에 따라 달라질 수 있습니다."

## 4. 페르소나 & 핵심 시나리오

| 페르소나 | 상황 | 핵심 가치 |
|---|---|---|
| 30대 직장인 A | 병원은 자주 가지만 소액이라 청구 안 함 | 자동 발굴 + "예상 12만 원" 훅 + 실손24 딥링크 |
| 40대 주부 B | 가족 4명 보험 관리, 어느 보험인지 모름 | 보험 통합 조회 + 가족 관리(Phase 2) |
| 50대 자영업자 C | 오래된 1세대 실손, 서류 청구 막막 | 미연계 병원 서류 체크리스트 + 제출 준비 패키지 |

핵심 여정 (Aha-moment까지 5분 이내):
가입(본인인증) → 동의(1·2층) → 데이터 연동(보험+진료, 간편인증 각 1회) → 홈에서 "예상 환급금 ○○원" 즉시 노출.

## 5. 기능 요구사항 요약

앱 5탭(홈/내 보험/환급금/간편청구/마이), 관리자 웹(RBAC 4롤), 백엔드 모듈(담보 매칭 엔진, 어댑터 계층, 필요서류 매트릭스, 알림)의 상세는 원문 사양서 §5~§7을 따른다. 세부 화면은 `02-wireframes.md`, 데이터는 `03-db-schema.md`, API는 `04-api-spec.md` 참조.

### 5.1 간편청구 라우팅 (핵심 분기)

```
진료건 선택 → 병원의 실손24 연계 여부 판별
├─ A. 연계 병원 → 실손24 딥링크 + 단계 가이드. 서류를 만지지 않음. 상태만 사용자 입력 트래킹.
└─ B. 미연계 병원 → 필요서류 체크리스트(보험사×청구유형×금액구간)
     → 서류 촬영/업로드(OCR) → (선택) 전문가 검토 → 제출 준비 완료 패키지
     → 최종 제출 버튼은 고객이 보험사 채널에서 직접.
```

### 5.2 금액 표기 정책 (전 시스템 공통 상수)

- 예측액은 항상 `예상 ` 접두 + 단일값 또는 구간값(물결 표기 금지).
- 산출 근거 미보유 건은 금액 미표기, "검토 필요"로만 표시.
- 면책 문구 컴포넌트 공통화, 예측액 노출 화면 전부 강제 포함.

## 6. 비기능 요구사항

- 전 구간 TLS 1.3. 필드 단위 암호화(AES-256-GCM): 진료내역·증권·연락처·CI. 키는 KMS 분리.
- 주민번호: 저장소·로그·백업·APM 트레이스 잔존 금지. 로그 마스킹 필터 + 정기 스캔 배치.
- 관리자 민감정보 열람 전건 감사 로그, 다운로드 금지(뷰어만).
- 진료내역 원본은 목적 달성(청구 완료 또는 사용자 삭제) 시 파기. 통계는 비식별화 후 보관.
- 홈 최초 로드 2초 이내(캐시), 연동 잡은 비동기 + 진행률.
- 외부 소스 장애가 코어 기능(조회된 데이터 열람, 보관함)을 막지 않도록 격리.
- 조회 캐싱: 진료내역 주 1회, 보험계약 월 1회, 수동 갱신 시 즉시 (건당 과금 비용 관리).

## 7. 수익 모델 및 전환 퍼널

```
무료: 예상 환급금 조회 (훅)
  → 무료: 청구 안내·서류 체크리스트 (신뢰)
    → 전환점 1: "내 보험 전문가 점검" → 설계사 리드 (수익)
    → 전환점 2: 복잡 건 "전문가 검토 요청" → 손해사정사 상담 (수익, 자격 범위 내)
```

청구 기능은 전면 무료 유지. 리드 단가·전환율이 유닛 이코노믹스 핵심 → 관리자에서 리드별 전환 추적.

## 8. KPI

| 영역 | 지표 | 목표 |
|---|---|---|
| 활성화 | 가입 → 데이터 연동 완료율 | 70%+ |
| Aha | 연동 완료자 중 미청구 발굴 경험률 / 1인당 평균 발굴 예상액 | 측정 후 기준선 |
| 전환 | 발굴 → 청구 진행률 / 청구 → 지급 확인률 | 측정 후 기준선 |
| 수익 | 상담 신청률 / 리드 전환율 / 리드당 수익 | 측정 후 기준선 |
| 신뢰 | 예측 대비 실지급 오차율 / 민감정보 CS | ±20% 이내 / 0건 |

## 9. Phase 범위

| Phase | 기간 | 범위 | 완료 기준 |
|---|---|---|---|
| 0 | ~1개월 | CODEF 샌드박스 PoC, 법무 자문 1차, 서류 매트릭스 상위 5사 초안, 와이어프레임 | 실데이터 조회 성공, 하드 룰 확정 |
| 1 (MVP) | 2~5개월 | 온보딩+홈+내 보험+환급금, 간편청구 B플로우, 관리자 최소기능, 동의 4층, 알림 | 클로즈드 베타 100명, 전환율 측정 가능 |
| 2 | 6~9개월 | A플로우 고도화, 가족 계정, 정확도 루프, 리드 자동화, 오픈 출시 | 오픈 출시 + 시드 데크 지표 |
| 3 | 10개월~ | 건강정보고속도로 신청, 공식 제휴 어댑터, 제휴 채널 확장 | 공식 소스 1개 이상 전환 |

## 10. 금지 사항 재확인

- 보험금 수령액 연동 성공보수 ❌ / 무자격 청구 대행 ❌ / 최종 제출 대행 ❌
- 주민번호 저장 ❌ / 포괄 동의 ❌ / 동의 목적 외 데이터 활용 ❌
- 확정액·예측액 혼용 표기 ❌ / 면책 문구 없는 예측액 노출 ❌
- 실손24 폄하·경쟁 프레임 마케팅 ❌ (공존·보완 포지션)
